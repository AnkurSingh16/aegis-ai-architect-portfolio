# Security runbook: local Auth0 case API

## Trust boundaries

- The browser's tenant path is only a requested resource selector. Authorization comes from a verified Auth0 `(iss, sub)` and a matching database membership.
- Auth0 issuer, API audience, and runtime database credentials are server configuration. Keep them in the ignored runtime-only `.env.api` locally and a secret manager for any later hosted environment. The broader `.env` is reserved for local Compose, migrations and administrator membership operations; never load it into the HTTP API process. Never print or paste bearer tokens or database URLs.
- The HTTP runtime uses `aegis_app`, a restricted non-owner role with forced RLS and SELECT-only membership access. The membership provisioning CLI requires separate administrator credentials and refuses the runtime role.
- The `north`/`south` fixture path remains for local synthetic CLI operations. Its server-controlled transaction mode is distinct from authenticated API mode. Fixture mode and its runtime credential are trusted local-server boundaries, not end-user authentication.

## Authentication and authorization

The verifier accepts Bearer JWTs signed with RS256 using JWKS at the fixed URL derived from the configured HTTPS issuer. It checks signature, issuer, exact API audience, expiry and not-before when present; subject and expiry are required. Runtime clients cannot set arbitrary JWKS URLs or test key resolvers. The protected API requires the signed `scope` claim. The database membership must also grant `reader` or `operator` as appropriate. Missing or invalid tokens return 401; missing scope or membership returns 403; an unavailable or foreign case is returned as not found.

Every protected operation uses one repeatable-read transaction. It sets transaction-local principal context, looks up membership, then sets tenant context and executes the operation on that same connection. RLS policies check the authenticated principal's membership and tenant context independently. Missing context defaults to deny. A request already in a repeatable-read transaction may complete using its snapshot after a concurrent membership revocation; new transactions observe the committed change.

## Local configuration and membership operations

1. Follow the Auth0 manual setup in the [README](../README.md#auth0-protected-case-api-milestone-2b). The API identifier is the JWT audience; the SPA client ID is not.
2. Copy `.env.api.example` to ignored `.env.api`. Set `AUTH0_ISSUER`, `AUTH0_AUDIENCE`, `AUTH0_SPA_CLIENT_ID` from the reviewed SPA output, and the restricted `DATABASE_URL` in that file. Keep administrator credentials in `.env`, which is used only by local Compose, migrations and membership administration. Start the server with `node --env-file=.env.api --import tsx apps/api/src/server.ts`. A partial Auth0 configuration fails startup; with both values absent, protected case routes are not registered.
3. Run the versioned database migration with the existing local migration command.
4. For a synthetic user, set `AEGIS_MEMBER_SUBJECT` to the exact verified Auth0 `sub`, `AEGIS_MEMBER_FIXTURE` to `north` or `south`, and `AEGIS_MEMBER_ROLE` to `reader` or `operator`. Grant using `node --env-file=.env --env-file=.env.api --import tsx apps/api/src/auth/membership-cli.ts grant`; revoke with the same issuer and subject and the `revoke` command. The CLI uses `DATABASE_ADMIN_URL`; never expose that credential to the API process.
5. For a real local smoke run, first create dedicated test user(s) manually in the Auth0 Dashboard. Do not use a customer identity. Use the same North reader identity for `authorized-north`, `insufficient-scope` and `cross-tenant`; use a separate identity without membership for `no-membership`. Run `node apps/api/scripts/auth0-pkce-smoke.mjs` in a normal interactive terminal and select one scenario. It reads only `.env.api`, validates the issuer/audience/client ID configuration, binds the fixed callback at `http://127.0.0.1:49321/auth/callback`, requests the scenario scope using PKCE S256, and calls only the loopback API. `insufficient-scope` requests no API permission; `missing-bearer` sends no Authorization header and does not open a browser. Expected responses are 200 for an authorized North reader and 403/403/403/401 for no membership, insufficient scope, cross-tenant, and missing bearer respectively. The bearer token and callback code stay in memory; never copy them from process memory, URLs, logs or browser developer tools. A membership grant is a separate administrator write and requires separate approval; use the exact subject (`sub`) from the test user's Auth0 identity only after that approval.

## Development browser case viewer

The optional React sign-in is enabled only in Vite development and uses the public values from `apps/web/.env.local`; never pass `.env.api`, `.env.auth0`, database credentials or Management API secrets through Vite. No Auth0 settings are changed by this feature, and production authentication remains disabled.

## Verification and failure response

Run `npm run lint`, `npm run typecheck`, `npm run test:coverage`, `npm run build`, and `npm run test:integration -w apps/api` against the dedicated local `aegis_test` database. Tests use local generated RSA keys/JWKS and synthetic data; they do not contact Auth0. Runtime failures return stable messages and structured request identifiers without token contents, subjects, connection strings or raw SQL errors. If a test shows cross-tenant access, missing-context access, unexpected membership writes, or a leaked credential, stop the local API, preserve sanitized logs, and investigate the migration, runtime role and RLS before continuing.

## Tenant-owned document storage foundation (Milestone 4.1)

Migration `003_tenant_documents.sql` adds `aegis.documents` and `aegis.document_chunks`. Document identity is tenant-scoped and versioned by stable synthetic source identity plus a positive version number. A new version is a new document row; chunks reference the exact tenant, opaque document UUID, document version, and source identity. Chunk order is unique within that version. Foreign keys enforce tenant, version, and provenance linkage in PostgreSQL.

The document record bounds owner/provenance/revision fields and JSON metadata; its source SHA-256 must have the expected lowercase hexadecimal form. Because the source document bytes are not stored, this schema does not prove that digest matches the source or that the owner claim is true. A future trusted synthetic-catalog ingestion process must validate provenance and compute the digest. Chunk text is capped at 8 KiB and PostgreSQL verifies its SHA-256 over UTF-8 bytes. No HTTP upload or ingestion path exists.

Both tables have RLS enabled and forced. Runtime SELECT requires `aegis.access_mode='authenticated'`, the matching transaction-local tenant, and a membership row for the transaction-local issuer and subject. The membership table's own RLS policy restricts that lookup to the verified principal context. Missing or mismatched principal, tenant context, or membership returns no rows. The `aegis_app` role has SELECT only on documents and chunks; it cannot INSERT, UPDATE, DELETE, or TRUNCATE them. Database administration and integration-fixture setup remain separate from the runtime role.

The migration runner applies migrations transactionally and verifies recorded SHA-256 checksums. Integration tests refuse non-loopback or non-`aegis_test` admin/runtime connection targets before fixture setup. This PR does not migrate `aegis_local`. A failed transactional migration is rolled back; do not edit migration 003 after it is recorded or perform an ad hoc schema rollback. Any rollback of a database where document data exists requires a separately reviewed, additive recovery plan and explicit approval. The runtime safety check now requires the six expected tables to have forced RLS and non-runtime ownership, validates intended grants, and fails closed for extra tables in the `aegis` schema.

Storage does not implement ingestion, retrieval, full-text search, embeddings, model calls, or HTTP endpoints. Those require subsequent reviews and tests; only synthetic source-controlled records are allowed for the initial corpus.

Apply, destroy, import, state commands and arbitrary Terraform arguments are denied. Review provider output before any future apply.

- Terraform state is held in the dedicated HCP Terraform `aegis-auth0-dev` workspace on the verified Free plan, with **Local execution** and auto-apply disabled. The local Terraform CLI token is held in Terraform CLI credentials and may also be represented in local backend metadata created by Terraform; both remain protected local files and are never printed or committed. Auth0 provisioner credentials remain only in ignored, mode-0600 `.env.auth0` on the local Mac. The restricted wrapper applies `umask 077` to Terraform processes and enforces mode `0600` on ignored `.terraform/terraform.tfstate` backend metadata and `.terraform/aegis-state-binding.json`; the latter records only workspace/state identifiers and a fingerprint of the expected resource inventory. Before initial remote initialization, the read-only preflight requires the exact organization/workspace settings and explicitly empty current-state relationship. On later `init` and `plan`, it also requires backend metadata and the pinned state version ID, serial and inventory fingerprint to match the marker. A missing or changed marker, state version, inventory, workspace or backend stops for manual review. Following a separately approved apply, inspect the current version and invoke the interactive `bind-reviewed-state` operation to update the local marker; type the displayed workspace and version ID. It performs no Terraform command and makes no HCP write. Never use migration, overwrite, import, state download, or unencrypted state copies. HCP state history supports recovery of prior versions; restrict workspace access. Provider cache remains local and ignored. Pull-request CI continues backend-disabled validation without HCP or Auth0 credentials.
- The ownership marker is a local consistency check protected by filesystem permissions, not cryptographic proof against compromise of the same macOS account. Rebinding requires independent operator review of the HCP workspace and its exact resource inventory; if ownership is uncertain, stop rather than bind.
- The preflight reads Terraform backend metadata and the ownership marker only from `infra/terraform/auth0/.terraform`; it reads HCP CLI credentials from the home-directory Terraform credentials file. The wrapper separately reads Auth0 provisioner credentials from repository-root `.env.auth0`. If the local bootstrap marker has a stale fingerprint, `repair-empty-bootstrap-marker` is available only after read-only checks prove HCP state is explicitly empty and module-local backend metadata matches the intended organization/workspace. This interactive command updates only the local marker and never initializes, migrates, or writes HCP state.
- The SPA is public, uses Authorization Code + PKCE, has no client secret, and is restricted to one loopback callback/origin. Access tokens still require the API's issuer/audience/signature checks, scope checks, database membership and RLS. The smoke harness keeps a real access token in memory for one request and does not persist or display it. Automated harness tests mock OAuth and API responses; only a separately approved operator run verifies a real Auth0 identity end to end.

## Controlled first Auth0 deployment

The first resource-creation path is the standalone `node infra/terraform/auth0/apply-first-deployment.mjs` entrypoint. Do not add apply to the standard `terraform-local.mjs` wrapper: its command allowlist is intentionally read-only. Tests and CI use mocks and must never invoke the standalone live entrypoint.

Before a separately approved first deployment, verify the HCP Free subscription, exact `aegis-ai-portfolio/aegis-auth0-dev` workspace, Local execution, auto-apply disabled, explicitly empty state, module-local backend fingerprint and protected bootstrap marker. Verify the configured Auth0 database connection and confirm that the API audience and SPA name are not already present. The gate performs these read-only checks before planning and again after the human confirmation.

The gate requires an interactive terminal, checks conventional CI/test/Codex execution markers as defense in depth, accepts no arguments, and asks for a fresh exact phrase that names the workspace and deployment intent. Environment markers are not an unforgeable identity boundary; a separate human approval must precede running the command. It prepares a short-lived Terraform saved plan in a mode-0700 directory, with a mode-0600 plan file. Structured plan JSON is parsed in memory; only the five documented Aegis resource addresses with exactly `create` actions are allowed. The plan is rechecked for unchanged file identity and content before the same saved file is applied. Terraform treats a saved plan as approved, so the gate's typed confirmation is the sole in-command approval; it does not pass `-auto-approve`. A saved plan can contain sensitive values even when output is redacted, so never copy, upload or print its contents. The gate cleans up the temporary directory on normal exit. After a crash or forced termination, the leftover artifact blocks another attempt and must be reviewed and removed manually.

If the operator cancels, no apply command runs. If an apply returns failure, assume it may have partially created resources or recorded partial state. Do not retry, destroy, restore an older HCP state version, import, or bind automatically. In the HCP workspace UI, inspect the latest state-version metadata and resource inventory without downloading the state file. Separately inspect the Auth0 Dashboard for the exact API, two scopes, SPA, and single database-connection association. Record which of the five resources exist and stop for manual recovery if there is any mismatch or uncertainty. Preserve the current HCP state version; do not replace or overwrite it.

After Terraform reports success, independently verify the same exact five-resource inventory in the HCP state and Auth0 Dashboard. Then run `node infra/terraform/auth0/terraform-local.mjs bind-reviewed-state` in a normal interactive VS Code Terminal, review the displayed workspace/state version/inventory, and type the requested confirmation. This updates only the local protected binding marker. Finally run `node infra/terraform/auth0/terraform-local.mjs plan`; expected output is zero adds, zero changes and zero destroys. Stop if binding verification or the no-op plan fails. A successful Terraform apply does not itself prove the application login or authorization flow; perform the separate local PKCE and protected API checks afterward.

## Controlled Auth0 SPA browser-origin and signing update

The browser-origin and JWT signing candidate uses the dedicated update workflow: `node infra/terraform/auth0/apply-browser-origin-update.mjs`. It is separate from the bootstrap-only first-deployment gate. Keep `terraform-local.mjs` read-only. The gate creates a private mode-0700 temporary directory and mode-0600 saved plan, then reads `terraform show -json` into memory without printing or persisting the JSON. The gate requires a genuine interactive TTY and a fresh typed confirmation naming the exact workspace, `auth0_client.local_spa` and displayed plan fingerprint. It takes no confirmation from arguments, environment variables or piped input, accepts no arbitrary Terraform flags, and does not use `-auto-approve`. Detected automation/agent environment markers are an additional defense, not proof of human identity; separate human authorization is still required. Terraform applies only the same saved plan after file-integrity and HCP state rechecks; Terraform's stale-plan check and state lock protect the final race window. Automated tests and CI use mocks only. Running or testing those mocks is not approval to apply; any live use still requires separate explicit human authorization after reviewing the implementation and fresh plan.

The diagnostic reports only allowlisted names and shape classes (`absent`, `null`, empty/nonempty array, empty/nonempty object, `other`, or `unavailable`); it never reports field values. For the sensitive field, it compares saved-state and refreshed-remote values in memory only when the pinned schema identifies a sensitive attribute, both source values exist, the sensitivity masks are present and shape-valid, and no unknown marker applies. ### State-only reconciliation boundary

A dedicated interactive read-only check is available as `node infra/terraform/auth0/plan-state-reconciliation.mjs`. It accepts no arguments and requires an interactive terminal plus the exact displayed plan-only phrase. It reuses the existing HCP preflight and binding marker, verifies the Free organization, exact workspace, Local execution, disabled auto-apply, current state version/serial/fingerprint and five-resource inventory before and after each Terraform read, then runs only `terraform plan -refresh-only` followed by `terraform show -json`. It never applies, refreshes, binds or writes state. Terraform documents refresh-only planning as a plan to align Terraform's state/output record with remote objects; it does not plan remote object changes. See [Terraform refresh-only planning](https://developer.hashicorp.com/terraform/cli/commands/plan) and the [Terraform JSON plan format](https://developer.hashicorp.com/terraform/internals/json-format).

The command stores the saved plan only in a fresh mode-0700 directory and requires a mode-0600 regular plan file. Plan JSON and provider schema stay in memory; stdout/stderr, values, identifiers and sensitive names are suppressed. It accepts only the exact five-resource inventory, one `auth0_client.local_spa` drift entry, the four reviewed null-to-empty shape changes (`allowed_clients`, `async_approval_notification_channels`, `client_aliases`, and `client_metadata`), one provider-schema-verified sensitive comparison equal to the saved value, no unknowns, no outputs changing, and no resource actions beyond no-op. Any missing, additional, malformed or unavailable evidence stops the workflow. It removes its fresh temporary directory on handled success/failure/cancellation. If the process is forcibly terminated or cleanup fails, the leftover artifact is not opened or deleted automatically; stop and inspect/remove it manually under the local file-handling policy. Filesystem unlinking cannot guarantee physical erasure on copy-on-write storage, so never copy or back up the plan.

Its code requires a direct TTY, refuses arguments and automation contexts, creates and validates a fresh private refresh-only plan, and never changes Auth0 configuration. This PR only prepares that gate; its existence, merge, or successful CI does not approve a live state write. Run it only after separate explicit operator approval for the exact candidate.

The gate displays the four transitions (`allowed_clients` null to empty array, `async_approval_notification_channels` null to empty array, `client_aliases` null to empty array, and `client_metadata` null to empty object) plus an explicit review warning. `allowed_clients` controls Auth0 client delegation/access associations; clearing the list changes which clients are associated. Review the effective behavior and confirm that the empty value is intended. If the impact is unclear, stop. The operator must type the exact review acknowledgment shown by the command, then a second exact phrase naming `aegis-ai-portfolio/aegis-auth0-dev`, the state-only intent, and the displayed SHA-256 of the saved plan. Applying a saved Terraform plan does not prompt, so this terminal confirmation is the authorization. The command verifies the plan fingerprint and the complete HCP workspace/backend/state-version/serial/inventory identity immediately before invoking `terraform apply` on that same saved plan with locking enabled. It never uses `-auto-approve`, accepts no arbitrary arguments, and never retries.

The state-only gate keeps the saved plan in a mode-0700 directory with a mode-0600 file and removes it on handled success/failure/cancellation. It emits only sanitized plan metadata and the SHA-256 fingerprint. Cleanup failure or forced termination requires manual artifact review; do not retry. Terraform state locking and stale-plan validation protect HCP state races, but they cannot lock Auth0 against an independent Dashboard/API change between refresh and apply. Run only in a reviewed low-change window; if you learn of any remote Auth0 change after planning, cancel and investigate rather than applying the stale plan.

After a successful apply, the gate verifies read-only that HCP has a new finalized state version, an advanced serial, the same workspace/backend identity, and the exact five-resource inventory. It does not update the local binding marker. Separately review and approve `node infra/terraform/auth0/terraform-local.mjs bind-reviewed-state`; inspect the displayed state version and inventory before confirming. If apply fails, is interrupted, or post-apply verification fails, assume state may have been partially written: do not retry, restore, import or bind. Inspect current HCP state-version metadata and inventory read-only and obtain a separate recovery review.

After an approved state-only reconciliation and verified local binding, the ordinary restricted Terraform plan is expected to contain exactly the separately approved pending browser/JWT update (zero adds, one in-place SPA change, zero destroys). It is not expected to be a no-op at that stage. A full no-op plan is expected only after that browser/JWT deployment has separately succeeded and been verified. On cancellation, plan mismatch, changed state or failed authorization, do not run apply. If apply is interrupted or fails part-way, assume Auth0 or remote state may have changed partially. Do not retry, destroy, restore/overwrite state, import, rebind or edit the Dashboard. ## Known limits

- This is a local foundation, not production authentication operations. Auth0 tenant configuration and secret management are manual; browser sign-in is development-only with an in-memory token cache. There is no production login, persistent refresh-token flow, rate limiting, cloud deployment or production monitoring.
- Database administrators can bypass RLS and remain trusted. Local fixture mode depends on trusted application code and runtime credentials.
- A case-change audit event records the case change but does not attribute it to the authenticated subject. Membership grant/revoke operations do not yet have a durable audit table.
- Repeatable-read transactions provide a consistent authorization snapshot. Revocation blocks new requests after commit but cannot cancel an already-running transaction.

## AI-assisted case analysis (Milestone 3A)

`POST /api/tenants/:tenantId/cases/:caseId/ai-analysis` is registered only outside production and within the authenticated case API. It requires the same verified RS256 access token, signed `read:cases` scope, issuer/subject membership and forced RLS as a case read. The endpoint reads the case using `withAuthenticatedTransaction`; inference begins only after that transaction commits and releases its connection. Invalid UUIDs, absent cases, no membership, missing scope and cross-tenant access do not call the provider. Request bodies with case text or other properties are rejected. The API never sends an unverified tenant record to a model.

The stored schema contains a synthetic fixture ID, status and timestamps; it does not contain a narrative. The provider prompt combines only those fields from the authorized row with the source-controlled synthetic case catalog entry selected by the stored fixture ID. The browser cannot supply or override this context. Treat future free-form case fields as untrusted prompt data and review the threat model before adding them.

Ollama is disabled by default. Explicit opt-in requires `AEGIS_AI_ENABLED=true` and a validated `AEGIS_OLLAMA_MODEL` while `NODE_ENV=development`; production rejects the opt-in and does not register the analysis route. The URL is fixed to `http://127.0.0.1:11434/api/generate`; redirects are rejected, there is no URL environment variable, proxy forwarding, cloud fallback or retry. A model must already be installed locally; Aegis never downloads one. The provider bounds prompts to 4 KiB, responses to 8 KiB, generation to 256 tokens, timeout to 1–30 seconds, and concurrent requests to one by default/two maximum. Client disconnects abort the request. These controls limit but do not eliminate local CPU, memory or latency costs.

Model output is untrusted. It must be valid JSON with exact keys, fixed enums for category/priority/team/next action, bounded rationale, numeric confidence, a known uncertainty level, unique evidence field references and `humanReviewRequired: true`. Unsafe recommendation text, unknown evidence fields, unknown keys, invalid metrics or malformed output fail closed. The response always says field references are not RAG citations or external grounding. Provider logs contain only provider/model labels, outcome, latency and optional token counts; prompts, case data, model output, credentials, tokens and raw errors are not logged. No recommendation is executed, and the API has no new status-write or escalation path.

The React analysis control is shown only with authenticated, server-authorized case rows. It uses an in-memory access token for same-origin `/api` calls with redirects rejected. Tenant, identity and session changes abort stale work and clear prior analysis; sign-out also clears the result. The UI renders the required human-review warning. The existing deterministic synthetic triage endpoint remains separate and is not used as an AI fallback.

Evaluation tests use synthetic cases and deterministic provider fixtures. Self-constructed outputs exercise schema and fixture-contract wiring; they are not independent model outputs or labels and do not measure model accuracy. CI mocks Ollama and makes no model/provider call. The bounded local evaluation completed on 2026-11-09; its measured results and limitations are in the [Milestone 3B.16 summary](AI-EVALUATION-3B.16.md). Do not present fixture-contract tests as model-quality evidence or the small local sample as production accuracy.

### Bounded local synthetic evaluation (Milestone 3B)

`apps/api/src/ai/evaluation` contains a versioned engineering evaluation set, deterministic scorer, and an explicitly invoked provider-level runner. The six planned slots are sequential: one canonical synthetic case and one timestamp-only paired observation for each of the three fixture types. Labels and rationales are fixed in source before model evaluation and marked engineering-reviewed, not human-approved. Timestamp pairs are not independent cases. Invalid-output probes are deterministic validator tests, never provider calls. The runner has no database or authenticated HTTP dependency and supplies only in-memory `StoredCase` objects built from the synthetic fixture catalog.

After the model and source are independently reviewed and a separate operator authorization is in place, the local-only command is:

